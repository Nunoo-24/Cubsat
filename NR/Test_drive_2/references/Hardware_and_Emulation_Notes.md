# Hardware and emulation research notes

Primary-source research for the initial one-axis software and hardware design.
These notes identify interfaces and constraints; they do not establish that a
part is present in the team's kit.

| Element | Primary-source finding | Project consequence |
|---|---|---|
| XIAO ESP32-S3 Sense | Seeed currently documents the Sense camera as upgraded to OV5640, while noting that boards in the transition may contain OV5640 or OV3660. The ESP32-S3 provides Wi-Fi and the Sense board includes PSRAM. | Keep camera initialization variant-aware and inspect the actual module. Measure available RAM and frame time at the selected resolution. The user selected the ESP32 as compute host; validate this with measurements. |
| Camera | Seeed's camera usage material covers OV5640/OV3660 variants, and its OV5640 module listing includes QVGA 320×240. | Begin target detection at low resolution and high contrast; calibrate optical centre/focal parameters on the assembled mount. Do not assume camera simulation equals real sensor performance. |
| XIAO Sense camera driver | Espressif's `esp32-camera` supports ESP32-S3 and OV3660/OV5640 and documents PSRAM use. A source cross-check against [Seeed's current camera pin table](https://wiki.seeedstudio.com/xiao_esp32s3_camera_usage/) confirms the firmware assignment: XCLK GPIO10; SCCB SDA/SCL GPIO40/39; DVP Y9..Y2 GPIO48,11,12,14,16,18,17,15; PCLK GPIO13; VSYNC GPIO38; HREF GPIO47. Seeed says the camera instructions are compatible with OV5640 and OV2640, and notes the Sense camera variant transition. | Firmware now has an optional grayscale QVGA capture adapter feeding the C target detector. The pin mapping matches the documented XIAO Sense board, but exact module identity, firmware compilation, image acquisition, and sensor performance remain unverified on the kit. Enable PSRAM and calibrate detector threshold/area/intrinsics on actual frames. |
| MPU-6050 | TDK/InvenSense specifies the bare MPU-6050 at VDD 2.375–3.46 V and VLOGIC 1.8 V ±5% or VDD; it is a 3-axis gyro/accelerometer with register-mapped I²C and configurable ranges. The XIAO exposes 3.3 V I²C on D4/GPIO5 and D5/GPIO6. | The user input describes a “5.5V MPU-6050”, which likely refers to a breakout input rating; the exact board-level regulator and I²C level shifting are not identified. Do not apply 5.5 V to the bare IC or assume its I²C lines are safe for the XIAO. The optional ESP-IDF driver reads raw XYZ, applies ±250°/s and ±2 g scaling, averages stationary startup gyro bias, configures DLPF_CFG=3 (42 Hz gyro bandwidth, 4.8 ms nominal delay) and SMPLRT_DIV=4 (200 Hz output), and estimates effective sample time by subtracting 4.9 ms filter delay plus up to 5 ms output phase. The datasheet reports 0.05°/s RMS total gyro noise at DLPF_CFG=2/100 Hz; this is a comparison point, not a guaranteed value for the unidentified breakout or the firmware’s DLPF setting. Verify breakout schematic/markings, power rail, pull-up voltage and axis map before wiring. The sample-time estimate is source-reviewed, not compiled or measured. |
| LIS3MDL | ST lists I²C/SPI, selectable ±4/8/12/16 gauss ranges, a 1.9–3.6 V chip supply, and marks the device out of production. The user prompt’s range/interface wording matches the LIS3MDL family. Adafruit’s LIS3MDL breakout guide describes a board variant with a regulator and level shifting for 3–5 V VIN/logic, addresses 0x1C/0x1E, and 3-axis magnetic output. This is a likely product match, not proof of the kit board/vendor/revision. | Firmware has an optional shared-I²C driver at ±4 gauss, 100 kHz, selectable 0x1C/0x1E, and raw µT telemetry. Its board-level 5 V tolerance applies only if the installed breakout matches the cited Adafruit design; the chip alone is not 5 V tolerant. The simulation rotates a fixed placeholder field. Magnetic calibration and motor interference remain unresolved; the physical field is not fused into control. |
| moteus r4.11 | mjbots specifies CAN-FD at 1 Mbit/s arbitration and 5 Mbit/s data rates. The r4 AUX2 connector is JST ZH-4; pins A/B are host TX/moteus RX and host RX/moteus TX. The UART defaults to 921600 8N1 on sufficiently recent firmware. It emulates fdcanusb over TTL UART: newline-terminated ASCII commands transport CAN-FD frames. Optional line CRC-8 uses polynomial 0x97; the official client includes a space before `*XX` in its checksum scope. Response lines carry checksums once checked commands are used. One host UART supports one moteus controller. Torque control is position mode with NaN position, zero velocity, zero kp/kd/integral scales, and feedforward torque. Native velocity mode uses NaN position and a velocity in rev/s; its command can specify a finite maximum torque and watchdog timeout. | **Do not connect ESP32-S3 TWAI directly to the moteus CAN-FD bus.** A simple transceiver cannot make TWAI FD-capable. A default-off ESP-IDF UART adapter is source implemented with a 1 mN·m default torque ceiling, finite 100 ms watchdog, explicit arm GPIO, status/fault query, torque mode and a bounded velocity commissioning path. The velocity frame writes the same `CUBESAT_MOTEUS_MAX_TORQUE_MNM` cap (Kconfig default 1, range 1–20 mN·m), so speed target support does not imply 3000 rpm/0.5 s capability. It uses XIAO D0/GPIO1 TX, D1/GPIO2 RX, and D2/GPIO3 arm by default to avoid the D6/D7 UART0 console pins; Seeed's pin map documents these GPIOs. The adapter remains uncompiled and unverified; check exact r4 firmware/configuration, connector mapping, electrical levels and independent emergency stop. A CAN-FD project requirement needs an external FD controller and transceiver. |
| ESP32-S3 CAN/TWAI | ESP-IDF documents the S3 TWAI peripheral as ISO11898-1 Classical CAN, with up to 8 data bytes; it explicitly warns that FD format frames are incompatible. The S3 provides general-purpose SPI master support. | A standard external CAN transceiver only handles the physical bus and does not add CAN-FD frame generation. To retain CAN-FD, an external FD controller and physical transceiver are required; the exact component, board, GPIO allocation, driver, timing, and bus termination must be selected and tested. |
| MCP2518FD candidate | Microchip identifies the MCP2518FD as an external CAN-FD controller with SPI interface, usable to add FD capability to a microcontroller without an FD peripheral. | This is a candidate adapter path only. Confirm breakout availability, separate CAN-FD transceiver, voltage/logic, clock, IRQ, SPI pins and driver maturity before choosing it. |
| ESP32-S3 emulation | Espressif QEMU supports ESP32-S3 CPU/memory and selected peripherals. Wokwi documents ESP-IDF and ESP32-S3 support and has a specific XIAO ESP32-S3 board model. | Wokwi is the selected first target-emulation candidate because board and Wi-Fi support fit the project. QEMU is useful for CPU/firmware-level checks. Neither replaces HIL for the listed camera, CAN-FD and motor. |
| ESP-IDF networking and JSON | The firmware uses ESP-IDF's HTTP client and cJSON. ESP-IDF 6 removed the former built-in `json` component; the project therefore declares Espressif's managed `cjson` dependency rather than relying on an IDF 5-only built-in component. | Resolve managed components and build with the declared ESP-IDF version before treating the C bridge as verified. Check the exact dependency component name and API against the installed IDF release during that build. |
| ESP-IDF control-loop scheduling | The installed ESP-IDF 6.1 FreeRTOS Kconfig defaults `CONFIG_FREERTOS_HZ` to 100 Hz. Its `xTaskDelayUntil()` API schedules periodic tasks against an absolute wake tick; relative `vTaskDelay()` accumulates work-time variation. | Firmware now explicitly defaults to 100 Hz (two ticks per 20 ms control period), schedules with `xTaskDelayUntil()`, and rebases after deadline misses. The SIL uses matching no-catch-up behavior. The task runtime/jitter has not been measured; verify on target. |

The simulation firmware currently performs synchronous HTTP work from the main
task and keeps a 2048-byte response body on the call path. The project therefore
sets the main-task stack to 8192 bytes and includes a debug-only high-water log
every 250 cycles. This is a provisional stack budget; measure free stack during
worst-case Wokwi and hardware transfers before treating it as adequate.

Research performed 2026-10-16. Recheck official documentation and the actual
kit before fixing implementation details; part availability and emulator
features can change.
